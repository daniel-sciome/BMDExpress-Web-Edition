1. Architecture Overview

The reactivity architecture is built on two distinct but complementary layers:

Hard Filter Layer

Defines the Working Set - categories that CAN be visible.

  • Primary Filter (4 parameters)
  • Filter Groups (5 preset + custom)
  • Persisted to localStorage
  • Changes do NOT reset visibility
Visibility Layer

Per-category visual state within the Working Set.

  • Visual states: highlighted, normal, dimmed, hidden
  • Additional properties: size, color, pinned
  • Driven by UI selections (table, charts, pickers)
  • Source-agnostic selection model

Key Design Principles

  • Separation of concerns: Filtering (what exists) vs. Visibility (how it's displayed)
  • State independence: Hard filter changes preserve visibility criteria
  • Per-category flexibility: Each category can have unique visual properties
  • Efficient storage: Only store overrides from default state
  • Generic groupings: Clusters, GO domains, pathways all use same pattern

3. Hard Filter Layer

The Hard Filter Layer determines which categories are included in the Working Set. Categories that don't pass these filters are excluded from all visualizations.

3.1 Primary Filter

Parameter Default Description
percentageMin 5% Minimum percentage of genes that passed filters
genesPassedFiltersMin 3 Minimum count of genes that passed all filters
allGenesMin 40 Minimum total gene count in category
allGenesMax 500 Maximum total gene count in category

Note: Primary Filter is skipped for GENE analysis type.

3.2 Filter Groups

Five preset filter groups, each containing multiple individual filters. Groups are enabled by default, but individual filters within are disabled until configured.

Group Fields Color
Essential: Gene Counts percentage, geneAllCount, genesThatPassedAllFilters Blue
Statistics: Fisher's & BMD Fisher's p-values, BMD/BMDL/BMDU statistics (24 fields) Green
Advanced: Counts & Percentiles 12 filter count fields + 6 percentile fields Purple
Advanced: Directional Analysis UP/DOWN directional stats (21 fields) Orange
Advanced: Fold Change & Scores Fold change, z-scores, model fold change (14 fields) Cyan

3.3 Persistence Behavior

  • Primary Filter values saved to localStorage on change
  • Filter Group configurations saved to localStorage on change
  • Restored automatically on app load
  • Critical: Changing hard filters does NOT reset visibility state

4. Visibility Layer

The Visibility Layer controls how each category in the Working Set is displayed. It uses a default + overrides pattern for efficient storage.

4.1 Visual States

A
Highlighted
Full opacity, emphasis
B
Normal
Standard display
C
Dimmed
Reduced opacity
D
Hidden
Not rendered

4.2 Per-Category Visual State

interface CategoryVisualState {
  visibility: 'highlighted' | 'normal' | 'dimmed' | 'hidden';
  size?: 'small' | 'medium' | 'large';
  color?: string;    // Optional custom color
  pinned?: boolean;  // Always visible regardless of other state
}

4.3 Storage Pattern: Default + Overrides

Instead of storing state for every category (potentially thousands), we only store categories that differ from the default:

interface VisibilityState {
  // Default state for categories not in overrides
  defaultState: CategoryVisualState;

  // Only categories with non-default state
  overrides: Record<string, Partial<CategoryVisualState>>;
}

// Example: 5 categories highlighted, rest dimmed
{
  defaultState: { visibility: 'dimmed' },
  overrides: {
    'GO:0001234': { visibility: 'highlighted' },
    'GO:0005678': { visibility: 'highlighted' },
    'GO:0009012': { visibility: 'highlighted' },
    'GO:0003456': { visibility: 'highlighted' },
    'GO:0007890': { visibility: 'highlighted' },
  }
}

4.4 Lookup Function

function getVisualState(categoryId: string, state: VisibilityState): CategoryVisualState {
  const override = state.overrides[categoryId];
  if (override) {
    return { ...state.defaultState, ...override };
  }
  return state.defaultState;
}

4.5 Initial State Behavior

Design Decision: All Categories Start Selected

When a dataset loads, all categories in the Working Set are initialized as "highlighted" (selected).

Rationale

  • Visual consistency: The initial view looks identical to before (all at full opacity)
  • Checkbox state: All checkboxes in the table start checked
  • Cluster picker: All clusters show "full" selection state (fully filled indicator)
  • User mental model: "Everything is selected" is easier to understand than "nothing is selected but everything is visible"
  • Deselection workflow: Users can click clusters or rows to narrow down (deselect) rather than build up (select)

Implementation

// When data loads, dispatch highlightCategories with all category IDs
const allCategoryIds = data.map(cat => cat.categoryId).filter(Boolean);
dispatch(highlightCategories({ categoryIds: allCategoryIds, exclusive: true }));
dispatch(setSelectedCategoryIds(allCategoryIds)); // Sync legacy selection

Behavior Comparison

Aspect Previous (None Selected) New (All Selected)
Visual appearance All rows full opacity All rows full opacity (same)
Table checkboxes All unchecked All checked
Cluster picker All show "none" state All show "full" state
Header tag No "Highlighted" tag Shows "Highlighted: N"
First click on cluster Highlights that cluster Deselects that cluster

5. Category Groups

Category Groups provide a way to organize categories into collections. Each group displays a tri-state selection indicator based on how many of its members are currently highlighted.

5.1 Tri-State Selection

None
0 of N selected
Partial
1 to N-1 selected
Full
N of N selected

5.2 Group Types

Type Source Example
umap_cluster UMAP dimensionality reduction Cluster 1, Cluster 2, ...
gene_cluster Active genes clustering Gene Cluster A, Gene Cluster B, ...

5.3 Data Structure

interface CategoryGroup {
  id: string;
  type: 'umap_cluster' | 'gene_cluster';  // Extensible for future types
  name: string;
  categoryIds: string[];  // Categories belonging to this group
  metadata?: Record<string, any>;  // Type-specific data
}

// Computed from visibility state
interface GroupSelectionState {
  groupId: string;
  totalCount: number;
  selectedCount: number;  // Categories with visibility: 'highlighted'
  state: 'none' | 'partial' | 'full';
}

10.3 Critical Behavior

Important: Filter Independence

When hard filter criteria change (Primary Filter or Filter Groups), the visibility state is preserved:

  • Selected category IDs remain in overrides
  • If a selected category is filtered out, it simply won't appear in Working Set
  • If filter is relaxed and category returns, it will still be highlighted
  • User doesn't lose their selection work when adjusting filters
